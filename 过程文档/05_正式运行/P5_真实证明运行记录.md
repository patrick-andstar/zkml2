## 2. 第一次尝试：OOM 失败（如实记录）

`p5_r18_128`，2026-11-15 16:09:50 起跑：

| 阶段 | 耗时 |
| --- | --- |
| SRS 生成 (k=23) | 356.91 s |
| vkey 生成 | 133.69 s |
| pkey 生成 | 79.12 s |
| 电路填充（内部 Mock） | 21.69 s |
| create_proof | 约 35 min 后被内核杀死 |

```
[MEASURE] wall=2714.314s max_rss=77.330GiB exit=-9
```

`exit=-9` = SIGKILL，`dmesg` 级的 OOM killer 行为。峰值 77.33 GiB 撞上 80 GiB cgroup 上限。

### 根因（不是模型太大，是代码持有冗余副本）

`src/utils/proving_kzg.rs::time_circuit_kzg` 有两处：

1. `let proof_circuit = circuit.clone();` —— clone 之后**原始 `circuit` 仍然活着**，直到函数结束。一份完整赋值 ≈ 10–12 GB。
2. `let _prover = MockProver::run(...)` —— `_prover` 绑定到局部变量，**不会立即释放**，整个 create_proof 期间都握着一份完整 MockProver（7.5M 行全赋值表）。这一项是大头。

### 修复（提交 `81734ac`）

```rust
-  let proof_circuit = circuit.clone();
-  let _prover = MockProver::run(degree, &proof_circuit, vec![vec![]]).unwrap();
+  let proof_circuit = circuit;          // move，不是 clone
+  let prover = MockProver::run(degree, &proof_circuit, vec![vec![]]).unwrap();
+  drop(prover);
```

**只改所有权，不改任何约束、见证或证明逻辑，也不改任何打印的计时值**（`fill_duration` 在其上方已经采样）。
实测峰值 RSS：**77.33 GiB → 66.18 GiB**。

> 注：`Time elapsed in filling circuit` 这个字段本身有边界错误（在 `MockProver::run` **之前**采样），
> 所以它只有 16.41 s，不代表真实填充耗时。**本轮所有结论以外部 `resource.getrusage` 实测为准。**

## 5. 数值交叉校验（关键，不是"约束满足"就完事）

电路暴露的输出（`expose_output=true`）是 1000 个定长整数，从 `public_vals` 解码（按 BN254 标量域模数取有符号值）：

```
count = 1000
argmax = 974
```

对照 P3 的浮点参考：

| 来源 | argmax |
| --- | --- |
| Keras 浮点参考模型（带显式 BN） | **974** |
| TFLite 导出模型（BN 折叠） | **974** |
| **zkml 电路公开输出（定长整数）** | **974** |

三方一致。这说明：定长量化 + 电路实现 + 证明过程在**语义层面**与原始浮点模型对齐，证明的不只是"约束自洽"。

> 局限：这只验证了 1 个样本的分类结果一致性，**不是**数据集准确率；也未验证逐层激活值误差界。
