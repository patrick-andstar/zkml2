# P4 电路可行性与资源预检

> 记录时间：2026-11-15 16:05–16:10 (GMT+8)
> 结论：**完整 ResNet18 128×128 的 MockProver 通过，峰值 34.39 GiB，落在 80 GiB 预算内，具备进入真实证明的资源条件。**

## 1. 行数与 k

用 `estimate_size` 对完整 model msgpack（含张量表）估算：

| 项 | 行数 |
| --- | --- |
| 赋值（张量表 + 随机向量） | 1,188,475 |
| 各层约束总量 | 6,337,706 |
| **合计** | **7,526,181** |
| 加盲化 | 7,526,196 |
| 取 k | **23**（2^23 = 8,388,608，余量 10.3%） |

> **坑：必须用 `*_model.msgpack`，不能用 `*_config.msgpack`。**
> `config.msgpack` 在设计上是"去掉 tensors 字段"的图，`estimate_size` 读到 `Total tensor + random size: 0`，
> 赋值行直接漏算 1,169,474 行，会给出 k=23 的假象而实际也够——但一旦模型更大就会算错 k。
> 这是本轮踩到的第二个隐式契约。

### 为什么行数远低于"MAC 数量"直觉

ResNet18@128 约 5.4 亿次乘加，若按"每次乘加一行"会得到 5 亿行、k=29 的结论——**这是错的**。

卷积被映射到 `FullyConnectedChip`，而 `implementation_idx=0` 走的是 **RLC（随机线性组合）累加**路径
（`src/layers/fc/fc_rlc_vdiv_*.rs`），不是 `num_rows_dot_acc` 的树形归约。它用一次随机线性组合代替
`O(log n)` 层归约，因此**每个点积只占大约 1 行**，而不是 `len/(num_cols/2)` 行。

按 `num_cols=10` 手算树形归约会得到 1.7 亿行、k=28、pkey 300 GB 的错误结论，从而误判"不可行"。
**实际是 k=23。** 这一条是本轮最重要的认知修正。

## 2. MockProver（完整网络，k=23）

```bash
test_circuit r18_128_model.msgpack r18_128_inp.msgpack
```

| 指标 | 值 |
| --- | --- |
| 输出 | **`Proof verified!`** |
| wall | 245.07 s（4 min 5 s） |
| 峰值 RSS | **34.39 GiB** |
| 覆盖范围 | 全部 50 个 layer，从 layer 0 Pad 到 layer 49 FullyConnected |

> MockProver 的 `Proof verified!` **不代表生成了密码学证明**，只代表所有约束在给定赋值下满足。

## 3. 资源预算（实测值 vs 80 GiB / 50 G 磁盘）

| 项 | 实测 / 外推 | 是否可承受 |
| --- | --- | --- |
| 电路赋值峰值 RSS（Mock） | **34.39 GiB** | ✅ 占 80 GiB 的 43% |
| KZG 参数 k=23 | ≈ 2^23 × 128 B = **1.07 GB** | ✅ |
| pkey k=23 | ≈ 2^23 × 1120 B = **9.4 GB** | ✅ |
| 磁盘合计（参数+pkey+proof+源码+target） | ≈ 12 GB / 50 GB | ✅ |
| 证明耗时 | 待 P5 实测 | 未知 |

### 外推公式（本节是本轮沉淀的核心资产）

由 MNIST k=15 实测标定（见 P2）：

```
params_bytes ≈ 128  × 2^k
pkey_bytes   ≈ 1120 × 2^k        (num_cols=10)
Mock 峰值 RSS ≈ 4.5 GiB × (rows / 1e6)   （由 34.39 GiB / 7.53M 行反推，粗略）
```

按此表，这台机器（80 GiB）的现实上限约在 **k=24～25**：

| k | pkey | Mock RSS（估） | 判定 |
| --- | --- | --- | --- |
| 23 | 9.4 GB | 34 GiB | ✅ 本轮 |
| 24 | 18.8 GB | 68 GiB | ⚠️ 极紧 |
| 25 | 37.6 GB | 136 GiB | ❌ |
| 26 | 75 GB | — | ❌ |

> `num_cols` 可以调节，但 pkey 大致 ∝ 行数 × 列数，而列数增大行数近似反比下降，
> 二者近似抵消，**不能靠调 `num_cols` 突破 k 上限**。真正的上限由"总乘加数"决定。

## 4. P4 结论

- 完整网络 Mock 通过，数值链路无 panic，k=23 与 10.3% 的行数余量都合理。
- 内存、磁盘均有充足余量，**判定：允许进入 P5 真实证明**。
- 未做降分辨率、未删层、未删残差。网络是完整的 ResNet18。
