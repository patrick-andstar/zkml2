## 30 秒速览

在 AutoDL 单卡 RTX 4090D 实例上（容器实配额 15 核 / 80 GiB / 80 GB 磁盘），成功把**完整 ResNet18**（18 层、8 个残差连接，无删减）以 **batch=1、RGB 128×128** 转换为 Halo2 电路（k=23，7,526,181 行），并生成了**真实的 KZG 证明**：证明生成 31 分 13 秒，proof 7,680 字节，验签 20 毫秒，峰值内存 66.18 GiB。证明在**独立进程**中二次验证通过；电路公开输出的分类 argmax 与浮点参考模型、TFLite 导出模型完全一致。**未使用预训练权重**，因此验证的是"完整网络 + 真实证明"的可行性，不是预训练模型的准确率。

## 2. 关键技术判断

### 2.1 为什么"5.4 亿次乘加"没有变成"5 亿行电路"

这是本轮最重要的一条认知。ResNet18@128 约 5.4 亿 MAC，直觉上电路行数应是同一量级，从而需要 k=29、pkey 数百 GB，直接判定不可行。

**这个推论是错的。** 读源码发现：卷积被映射到 `FullyConnectedChip`，而 `implementation_idx=0` 走的是 **RLC（Random Linear Combination）累加器**路径，不是 `num_rows_dot_acc` 的树形归约。它用一次随机线性组合把整个点积压进**大约 1 行**，而不是 `len/(num_cols/2)` 行。

实测结果：**7,526,181 行，k=23**。比朴素估算少 20 倍以上。

> 教训：这类系统的可行性必须**实测**（`estimate_size` 是纯 CPU、秒级），凭 MAC 数量推算是会得出相反结论的。

### 2.2 三个会静默炸掉的隐式契约

上游 README 都没写，全部是踩出来的：

| 契约 | 违反后果 | 处理 |
| --- | --- | --- |
| `num_randoms` 必须 ≥ 最大的 `batch·oh·ow` | 转到第一个卷积就 `Option::unwrap()` panic：`Random vector is too small: 4096` | 用默认 20001（1024 不够） |
| `estimate_size` 必须喂 `*_model.msgpack`，不是 `*_config.msgpack` | 赋值行被漏算（本轮漏 116 万行），k 会算小 | 用 model 文件 |
| `MaxPool2D` 不接受 SAME padding | 转换直接 `NotImplementedError` | 全改显式 `ZeroPadding2D` + VALID |
| 没有独立 `RELU` 层 | 若有未融合的 ReLU，转换器无分支报错 | 确保 ReLU 融进 CONV/ADD |
| 没有 BatchNorm 层 | 图里出现 MUL/SUB，语义错 | BN 解析式折叠进卷积 |

### 2.3 OOM 不是"模型太大"，是代码持有冗余副本

第一次运行在 77.33 GiB 撞上 80 GiB 上限被内核杀死（撑了 45 分钟）。根因是 `time_circuit_kzg` 里两处冗余持有：

1. `circuit.clone()` 之后原始 `circuit` 仍活到函数结束（≈10–12 GB）；
2. `let _prover = MockProver::run(...)` 把一份完整 MockProver 表**一直握到 create_proof 结束**（大头）。

改成 move + `drop(prover)` 后，峰值 77.33 → **66.18 GiB**，一次通过。**未改动任何约束、见证或证明逻辑。**

## 3. 实测指标汇总

| 指标 | MNIST（k=15） | **ResNet18@128（k=23）** | 倍数 |
| --- | --- | --- | --- |
| 电路行数 | 20,199 | **7,526,181** | 373× |
| 证明生成 | 8.27 s | **1873.29 s** | 226× |
| proof 大小 | 3,360 B | **7,680 B** | 2.3× |
| 验签耗时 | 16.83 ms | **20.44 ms** | 1.2× |
| 峰值 RSS | 241 MiB | **66.18 GiB** | 281× |
| KZG 参数 | 4.2 MB | 1.02 GiB | 256× |
| pkey | 36.7 MB | 11.26 GiB | 315× |

注意 proof 大小和验签耗时几乎不随电路规模增长——这是 SNARK 的固有性质，也是它相对"重新执行一遍"的价值所在。

### 资源外推公式（可复用）

```
params_bytes ≈ 128  × 2^k
pkey_bytes   ≈ 1440 × 2^k        (num_cols=10，k=23 实测)
证明耗时      ≈ O(rows log rows)，15 核下 7.5M 行 ≈ 31 min
```

这台机器（80 GiB）的上限大约在 **k=24**（pkey 约 24 GB，峰值可能 100 GB+，需要实测）。`num_cols` 调大不能让 k 变大：列数增大、行数近似反比下降，二者抵消。

## 4. 问题—风险—对策—趋势

| 问题 | 风险 | 对策 | 趋势判断 |
| --- | --- | --- | --- |
| 用随机权重，未验证预训练模型 | 结论不能外推到"ImageNet ResNet18 的 ZK 推理正确" | 需补 torch→TF 权重迁移 + BN 折叠校验 | 权重迁移是纯工程问题，1–2 天可解 |
| 定长量化误差未逐层界定 | 深层网络可能溢出或精度崩塌而 argmax 侥幸正确 | 需加逐层激活导出 + 与浮点逐层比对 | 这是最容易被审稿人打的点 |
| k=24 以上内存不够 | 想跑 224×224 必须换机型 | 需 256 GB+ 内存实例，或改用 IPA/Halo2 优化 | 硬件是硬约束，算法侧短期无解 |
| pkey 每次重算（75 s）+ 12 GB 磁盘 | 反复实验会快速吃掉 50 GB 数据盘 | 参数与 pkey 应做缓存复用 | 工程问题，容易解 |
| 上游代码有计时边界错误 | 用程序自报数据会低估填充耗时 | 一律外部测量 | 已在报告中标注 |
| 上游 git 在服务器上不稳（TLS 中断） | 源码版本可能与本地不一致 | 用 SSH 直传 + md5 校验 | 已在 manifest 里记录 md5 |

## 5. 复跑命令

```bash
# 1. 环境（一次性）
#    Rust: sh.rustup.rs, --default-toolchain nightly --profile minimal，RUSTUP_DIST_SERVER 走清华镜像
#    Python: conda create -n zkml311 python=3.11
#            pip install numpy==1.23.5 msgpack==1.0.5 tensorflow-cpu==2.12.0 tflite==2.10.0
export PATH=/root/.cargo/bin:$PATH
export CARGO_TARGET_DIR=/root/autodl-tmp/zkml2/target
cd /root/autodl-tmp/zkml2 && cargo build --release          # 5m15s，零补丁

# 2. 导出 + 转换（cwd = 任意工作目录）
python scripts/resnet18_export.py --size 128 --output r18_128
python python/converter.py --model r18_128.tflite \
  --model_output r18_128_model.msgpack --config_output r18_128_config.msgpack \
  --scale_factor 512 --k 23 --num_cols 10 --num_randoms 20001

# 3. 行数确认（必须用 model，不是 config）
./target/release/estimate_size r18_128_model.msgpack        # 期望 7,526,181

# 4. 输入
python -c "import numpy as np;np.save('inp.npy',np.random.default_rng(20261115).random((1,128,128,3),dtype=np.float32))"
python python/input_converter.py --model_config r18_128_config.msgpack --inputs inp.npy --output inp.msgpack

# 5. 约束检查
./target/release/test_circuit r18_128_model.msgpack inp.msgpack    # 期望 "Proof verified!"

# 6. 真实证明（需 cwd 下有 params_kzg/）
mkdir -p params_kzg && ./target/release/time_circuit r18_128_model.msgpack inp.msgpack kzg

# 7. 独立验证
./target/release/verify_circuit r18_128_config.msgpack vkey proof public_vals kzg
```

## 6. 可能的追问与回答思路

**Q1：proof 只有 7.6 KB，能说明什么？**
结论先行：说明证明大小与电路规模解耦，这是 SNARK 的核心价值。依据：MNIST（2 万行，3,360 B）到 ResNet18（753 万行，7,680 B），行数涨 373 倍，proof 只涨 2.3 倍；验签耗时 16.8 ms → 20.4 ms。所以验证方成本几乎不变，代价全部压在证明方（31 分钟、66 GB）。

**Q2：为什么不用预训练权重？是不是避重就轻？**
不回避：这是本轮的明确缺口。理由是先把"完整网络能否进电路、能否真的出证明"这个可行性问题分离出来——它才是风险最高的部分，而权重迁移是确定性工程。其次，`scripts/resnet18_export.py` 的接口已经按"可注入权重"设计（当前用 He 初始化），换权重不改图结构，行数、k、证明代价都不变。

**Q3：80 GiB 内存真能跑 128×128，是不是哪里省了？**
没有省。8 个残差全部保留、20 个卷积一个不少、输入就是 128×128×3。k=23 是 `estimate_size` 对完整 model 文件算出来的，不是拍脑袋。之所以比直觉便宜，是因为 RLC 累加器把整个点积压进约 1 行（见 2.1）。同时也要说清：**k=24 就很紧张，224×224 这台机器跑不了。**

**Q4：这个跑通了，能直接写论文吗？**
不能。缺三块：预训练权重、逐层定长误差界、多批量/数据集层面的正确率。当前成果的正确定位是"可行性验证 + 一套可重放的工程基线"。真正可写的是"定长量化在深层残差网络中的误差传播与约束规模"这个题，而它的前提（能不能跑通完整网络）现在已经解决了。

**Q5：改动了上游代码，还算复现吗？**
改动只有一处、六行，且是纯内存所有权调整（`clone` → move，加 `drop`），不触碰约束、见证、证明与验证逻辑，也不改变任何打印的计时值。上游改动以独立提交 `81734ac` 记录，diff 可审。除此之外 `cargo build` 在 2026-11-12 的 nightly 上**零补丁通过**。
